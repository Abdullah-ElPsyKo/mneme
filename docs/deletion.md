# Memory lifecycle in Mneme 0.2.2

## Object audit and semantics

| Object                                                             | User action and canonical behavior                                                                 | Dependencies and retained data                                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Memories, notes, captures, documents, projects, other memory types | Delete in inspector or editor; create an `archived` revision through the existing save/outbox path | End live edges and reject pending proposals targeting it. Keep child notes, tasks, free-text project labels, originals and prior revisions.                                                                                                                                             |
| Standalone entities                                                | Delete in inspector; append `entity.archived`                                                      | End live edges and reject proposals targeting it in the same transaction. Keep endpoint rows for foreign keys and historical graphs. Memory-backed entities use memory archival.                                                                                                        |
| Relationships                                                      | Delete in Connections; set `valid_until` and append the existing `relationship.ended` event        | Keep both endpoints and historical edges. Restoring a memory does not silently restore ended edges.                                                                                                                                                                                     |
| Tasks                                                              | Delete beside task controls; append `task.archived`                                                | Exclude from every task filter and current counts. Keep the row, version history, linked memory and project. Further edits to a deleted task are rejected.                                                                                                                              |
| Imported sources                                                   | Delete beside Original in Sources; append `source.archived`                                        | Hide only the catalogue entry. The confirmation explicitly says the linked memory remains searchable. Immutable original bytes and IDs stay available to every surviving/historical reference. Delete the linked memory separately to remove its extracted text from current retrieval. |
| Ask turns                                                          | Delete beside the question, after generation finishes; append `ask.archived`                       | Hide from Ask history. Keep audit events, stored answer/context and cited memories. A running turn cannot be deleted; stop generation first.                                                                                                                                            |
| Structured records / measurements                                  | Timeline → record-created event → Delete; append `record.archived`                                 | Hide from current record queries. Keep supersession references and history. These records had no dedicated list/editor view, so the existing Timeline detail is their action surface.                                                                                                   |
| Pending proposals                                                  | Delete beside suggestion actions; reuse the existing rejection operation                           | Keep evidence/review history; never apply the suggestion. An accepted proposal remains audit history; delete the resulting object instead.                                                                                                                                              |

The actions above archive current state. The separate **Delete permanently** action for memories is described below. Every action uses a Mneme modal, identifies the target and explains consequences before mutation. Cancel, Escape and closing the modal do not mutate data. The backend requires explicit confirmation plus a preview revision hash; changed content/connections require another review.

Memories remain recoverable: Timeline → open a memory event → Open current memory → History → choose a prior active revision → Restore as new revision. Other archives retain their canonical/audit data but do not introduce a new restore/trash UI in this focused change.

## Consistency and recovery

- One domain deletion service supplies previews and validated mutations. The UI does not perform dependency maintenance.
- Memory metadata, revision event, Markdown outbox entry, edge endings and dependent proposal rejections commit in the same SQLite transaction. Existing fsync/atomic replacement and outbox replay publish the archived Markdown. An interrupted flush is recovered on restart.
- Archived memory content is removed from FTS documents, chunks and vectors. A lightweight indexed-revision marker remains for consistency checking. Rebuild and startup repair preserve this exclusion; current retrieval also checks canonical status, and context compilation excludes archives even if an explicit archived-status query is supplied.
- Background embedding publication rechecks the canonical revision, status and privacy flag in its SQL write, preventing a model response started before deletion from republishing a vector. Consolidation skips deleted memories/entities. Stale external Markdown can update retained archived content but cannot silently reactivate it.
- Current graph queries exclude archived standalone entities and memory-backed nodes. Ended edges remain queryable only as historical connections; endpoint foreign keys remain valid.
- Source bytes are never unlinked by archival. Their content-addressed identity can be shared by imports, recovery objects, revisions, proposals and Ask evidence.
- Schema migration 3 adds an event-kind/aggregate index and marks the minimum reader version for archival semantics. Existing data is unchanged. Older binaries refuse the newer brain instead of reopening it while ignoring deletion markers. No second canonical format or archive table is introduced.

## Permanent memory deletion

Available in the memory inspector and editor, including archived memories opened from Timeline. A separate modal explains the scope, retained backups and shared sources, and requires an acknowledgment checkbox. It is not an archived revision and creates no content-bearing deletion event.

Removed from the active brain:

- The memory row, Markdown, pending Markdown writes, all memory revision/history/provenance events, and its memory-backed entity.
- All attached graph relationships, including ended relationships, and their events.
- Referencing tasks, structured records, proposals (including accepted/rejected ones), and saved Ask turns, including their events. Dependent records are removed as complete units because their text/answers can quote the erased evidence. This can remove a saved answer that also cited other memories; those other memories remain.
- Jobs referencing removed IDs. Deletion waits for running jobs, backups and Ask generation to finish; retry after they finish.
- Exclusive imported/recovery source records and object files. References from surviving memories, revisions, entities, sources, proposals, records, tasks, Ask turns and jobs protect shared originals. Shared sources lose their link to the deleted memory but remain readable.
- FTS documents/shadow data, chunks, vectors, indexing/stat caches and diagnostic/reconciliation state. Derived indexes are rebuilt from surviving memories. Interrupted atomic-write copies and identifiable stale Markdown copies within the vault/object store are also removed.

Surviving memory revisions have deleted supersession/provenance references redacted; current Markdown is republished through the outbox. Other memories retain their own content and revision numbers. Event update/delete guards are suspended only inside the explicit erasure transaction and restored before commit; rollback restores both data and guards. Normal writes remain append-only.

**Failure handling:** canonical removal and a durable cleanup journal commit together. A database failure rolls everything back before any files are removed. A subsequent filesystem/index cleanup failure returns an explicit incomplete-cleanup error, keeps the journal and blocks API access, memory writes and background work. Restart retries cleanup before opening the brain. Once filesystem deletion starts, rollback would be unsafe; the operation must finish forward. SQLite secure-delete, FTS rebuild, VACUUM and WAL truncation remove old content from the managed databases before success is reported.

**Intentionally retained:** schema/sequence information and SHA-256 fingerprints of the erased UUID and known revision/original-byte hashes. These contain no title, body, facts or raw UUID and prevent stale Markdown or known original files from being reimported. The temporary journal contains only managed file paths and is removed after successful cleanup. Shared original evidence remains, as described above.

**Limits:** existing backups (including the brain's backup folder), exports, provider-side copies and external copies remain unchanged. Restoring a backup made before deletion restores its old contents. Backups made afterward preserve the erasure fingerprints. Manually rewritten copies with removed IDs and different bytes cannot reliably be identified as the erased memory; independently authored/copied text in other memories is not searched and deleted by content similarity. This is application-level erasure, not a guarantee against disk/SSD forensics or operating-system snapshots. Settings and content-free service logs remain unchanged.

## Multiple facts and supersession

`facts` is an ordered JSON array of `{key, value}` string pairs, stored in the memory row, revision events and YAML frontmatter. Zero to 100 facts are supported within the existing 64 KiB total frontmatter limit; oversized metadata is rejected before saving. The editor provides Add fact and Remove row controls; units stay part of each value string. Context evidence and conflict detection cover every fact. Validity dates and supersession still apply to the whole memory.

Migration 4 adds the JSON column and erasure tables, converting each existing nonempty single fact into one array entry without rewriting its Markdown or historical events. Historical reads normalize legacy single facts. Legacy API/frontmatter inputs remain accepted; `fact_key`/`fact_value` mirror the first fact for compatibility, while an explicitly supplied `facts` array is authoritative (including `[]`). Older binaries refuse schema 4.

The Supersedes picker searches titles/projects, ranks the same project first, and displays titles, project and date. It excludes the current memory, descendants that would cause a cycle, and archived candidates; already-superseded candidates are labeled. Existing archived references remain visible by title. Selection can be changed or cleared; the stored reference remains the UUID and server-side cycle validation remains in place.
